# Формат ArenaTES3JSON v1

Корневой JSON содержит `format`, `format_version`, сведения об исходнике и массив `records`.
Порядок записей и подзаписей является значимым и сохраняется.

Каждый TES3 record хранит:

- `type` — 4-байтовый идентификатор (`TES3`, `CELL`, `NPC_`, ...);
- `unknown` — исходное 32-битное поле заголовка;
- `flags` — исходные 32-битные флаги;
- `subrecords` — подзаписи в исходном порядке;
- `tail_b64` — необязательные байты в конце payload, если они не образуют стандартный subrecord.

Строковые subrecord'ы, которые можно без потерь декодировать, имеют:

```json
{
  "type": "NAME",
  "size": 12,
  "encoding": "windows-1251",
  "data_b64": "z/Do7OXwAA==",
  "data_sha256": "...",
  "text": "Пример",
  "trailing_nuls": 1
}
```

`data_b64` и `data_sha256` сохраняются для каждой подзаписи, включая текстовые.
Бинарные подзаписи имеют `encoding: "binary"` и используют `data_b64` напрямую.

Для `encoding: "windows-1251"` правила импорта такие:

- если `data_b64` не менялся (его SHA-256 совпадает с `data_sha256`), используется поле `text` и оно кодируется в CP1251;
- если `data_b64` изменён, raw-байты считаются намеренной правкой и имеют приоритет над `text`;
- старые JSON v1 без `data_b64` у текстовой подзаписи остаются совместимыми: используется `text`.

Поле `size` информационное: при обратной сборке размер вычисляется из фактических данных.

## Почему round-trip не должен менять файл

ArenaTES3JSON не преобразует ESP/ESM в высокоуровневую объектную модель и не создаёт записи заново по правилам движка. Он сохраняет порядок records/subrecords, `unknown`, `flags` и каждый payload. Для неизменённого JSON это позволяет получить те же байты, а self-test и CLI `--verify` проверяют это напрямую.
